# MangaHere for Paperback 0.9 — Design Specification

Date: 2026-08-28
Status: Approved in chat; awaiting written-spec review
Owner: indigoxred

## 1. Objective

Build a standalone MangaHere source extension for Paperback 0.9 that:

- reconnects titles and chapters restored from Netsky's Paperback 0.8 `MangaHere` source;
- supports current MangaHere browsing, search, metadata, chapters, and page loading;
- improves traditional-reader startup time by replacing unnecessary serial page resolution with safe bounded concurrency;
- installs and updates through a single Paperback repository URL; and
- is developed in a new private repository owned solely by `indigoxred`.

The repository will not be a fork, will not import another repository's Git history, and will not submit or require changes in anyone else's repository.

## 2. Constraints and Assumptions

- The Paperback source identifier must remain exactly `MangaHere` so restored library records can find the replacement source.
- The source repository is private. Only compiled installation artifacts and required manifest/assets are published to a public, unlisted endpoint that Paperback can fetch without authentication.
- A client-downloadable extension cannot be treated as secret. Minification may reduce readability but is not a security boundary.
- GitHub Pages deployment from a private repository requires a GitHub plan that supports it. Repository visibility must not be changed automatically if that prerequisite is unavailable.
- MangaHere's traditional reader requires a separate resolver request for each page. The extension can reduce unnecessary waiting but cannot eliminate site-required requests.
- Paperback expects a complete ordered page list from chapter-details resolution; progressive streaming is outside the current design.
- Final reader behavior must be checked on the owner's Paperback 0.9 device.

## 3. Architecture

The project will use a fresh Git repository named `indigoxred/mangahere-paperback`. It will contain one Paperback source and a static repository distribution generated by the supported Paperback 0.9 toolchain.

The source is divided into focused components:

1. **Source adapter** — Paperback-facing search, discovery, metadata, chapter, and chapter-details methods.
2. **Identifier normalizer** — accepts legacy Paperback 0.8 IDs and modern path-shaped IDs, then converts both to one internal representation.
3. **MangaHere parser** — extracts search results, title metadata, chapter lists, and reader configuration from fetched documents.
4. **Page resolver** — handles bulk/webtoon image extraction and bounded-concurrency traditional-page resolution.
5. **Request policy** — separates ordinary browsing limits from the narrowly scoped page-resolver queue and implements retry/backoff behavior.
6. **Repository packager** — produces Paperback manifests, source bundles, icons, and version metadata.
7. **Deployment workflow** — tests, builds, and publishes versioned artifacts to GitHub Pages without exposing the private source repository.

Dependencies between these components are one-directional: the Paperback adapter calls normalization and parsing/resolution services; parsing and resolution do not depend on Paperback UI behavior. This keeps compatibility and concurrency logic independently testable.

## 4. Identifier Compatibility

The normalizer must accept at least these equivalent forms:

- Legacy title ID: `series-name`
- Path-shaped title ID: `manga/series-name`
- Absolute title URL: `https://www.mangahere.cc/manga/series-name/`
- Legacy chapter ID: `c025`
- Path-shaped chapter ID: `manga/series-name/c025`
- Absolute chapter URL: the equivalent MangaHere chapter URL

Normalization removes the host, query string, fragment, redundant slashes, leading slash, optional `manga/` prefix, and trailing slash. It validates the remaining slug/path before constructing a request URL.

Newly discovered titles and chapters will emit the stable legacy-compatible form: a title slug and chapter leaf ID. This avoids creating a second library identity for content already restored from Paperback 0.8. The request layer still accepts path-shaped forms so entries created by other 0.9 builds remain usable.

Chapter URL construction uses both `mangaId` and `chapterId`. A legacy chapter leaf is joined to the normalized title slug; a full chapter path is validated and used directly.

## 5. Chapter Page Data Flow

1. Normalize the incoming title and chapter identifiers.
2. Fetch the chapter document using the ordinary request client and session/cookie policy.
3. Detect the reader mode.
4. For bulk/webtoon mode, decode the page array already embedded in the chapter response and return it in source order.
5. For traditional mode:
   - extract and validate the page count, chapter resolver ID, secret key, and image base URL;
   - enqueue one resolver job per page;
   - execute jobs with an initial concurrency limit of three;
   - decode each resolver response into a final image URL;
   - store results by their zero-based page index; and
   - return URLs only after every index is present and valid.

The initial concurrency of three is deliberately conservative. It is an internal policy value, not a user-facing setting. Device and integration results may lower or raise it before the first stable release.

## 6. Failure and Throttling Behavior

- Transient network failures and malformed/empty resolver responses retry per page with short bounded backoff.
- Retry attempts are limited to three per page.
- HTTP 403 or 429 responses are treated as blocking/throttling signals. The resolver reduces effective concurrency and retries; persistent throttling falls back to sequential resolution.
- If MangaHere's known empty-key fallback is required, it is attempted only for the failed page rather than restarting a successful chapter.
- Results from successful jobs remain indexed, but the extension never returns a partial chapter. Any page still unresolved after retries produces a clear chapter-resolution error.
- Logs may contain source, chapter, page index, HTTP status, attempt number, and timing. Cookies, authentication material, secret headers, and full response bodies must not be logged.
- Parser failures distinguish removed/invalid content from temporary site-layout changes where practical.

## 7. Performance Measurement

The benchmark compares the reference serial policy with the new resolver on the same representative traditional-reader chapters.

Capture:

- chapter page count;
- time from chapter-details request start to complete ordered page list;
- request/retry count;
- throttling responses; and
- missing, duplicated, or reordered URLs.

The initial acceptance target is at least a two-times improvement in median resolver time for representative 20–40 page chapters, with zero missing, duplicated, or reordered pages. Correctness and avoiding site blocks take priority over the speed target.

## 8. Testing Strategy

### Automated unit tests

- Normalize all legacy, path-shaped, absolute, malformed, and boundary-case IDs.
- Construct chapter URLs from every supported title/chapter ID combination.
- Parse representative search, metadata, chapter-list, bulk-reader, and traditional-reader fixtures.
- Decode representative obfuscated image resolver responses.
- Prove that concurrent jobs return pages in source order even when responses complete out of order.
- Cover retries, empty responses, 403/429 throttling, concurrency reduction, sequential fallback, and terminal failure.

Fixtures will be minimal and sanitized. They will contain only the markup/script fragments required to exercise parsing behavior.

### Live integration checks

- Use a small request set against a current search page, title page, bulk/webtoon chapter if available, and traditional chapter.
- Validate response shape and URL reachability without downloading entire image sets unnecessarily.
- Avoid aggressive repeated benchmarks against the production site.

### Device acceptance

The owner will test the published development repository in Paperback 0.9 using:

1. one title restored from a Paperback 0.8 backup;
2. one newly searched title;
3. at least one bulk/webtoon chapter, if available;
4. traditional chapters of different lengths; and
5. an extension update through the same repository URL.

## 9. Build and Deployment

- The private repository uses the supported Paperback 0.9 SDK/build tooling locked to explicit dependency versions.
- Pull/push checks run formatting, static analysis/type checking, unit tests, fixture tests, and a production build.
- A versioned release workflow generates the repository manifest and source bundle, then deploys only required distribution files through GitHub Pages.
- The install URL remains stable across releases.
- Deployment uses GitHub's built-in workflow permissions and does not place long-lived personal tokens in source control.
- If private-repository Pages is unavailable for the owner's plan, work pauses with a reported prerequisite. The repository must not be made public and an alternative host must not be added without explicit approval.

## 10. Acceptance Criteria

The first stable release is accepted only when:

- Paperback 0.9 installs the source from the published repository URL;
- the installed source ID is exactly `MangaHere`;
- a restored Paperback 0.8 MangaHere title reconnects without library recreation;
- old and new ID formats open the same title and chapters;
- search, metadata, chapter listing, and both reader modes work on current MangaHere pages;
- traditional chapters contain every page exactly once and in reading order;
- resolver failures back off or fall back without silently returning partial results;
- the measured performance target is met, or a documented site-safety reason justifies a lower concurrency policy;
- the same URL provides a subsequent test update; and
- no source-repository visibility or external-repository change occurred.

## 11. Out of Scope

- Changes to Paperback itself.
- Migration of sources other than MangaHere.
- Publishing to Inkdex or any third-party extension registry.
- Pull requests or releases in another maintainer's repository.
- Circumventing Cloudflare, CAPTCHAs, authentication, or durable access controls.
- Promising secrecy for a bundle that must be downloaded by the client.
- A user-facing concurrency setting before evidence shows it is necessary.

## 12. Delivery Sequence

1. Create the private GitHub repository and local development checkout.
2. Establish the Paperback 0.9 build/test baseline.
3. Implement compatibility normalization and source functions test-first.
4. Implement reader parsing and bounded resolution test-first.
5. Run live integration checks and resolver benchmarks.
6. Configure the public, unlisted distribution endpoint.
7. Publish a development build for owner device testing.
8. Incorporate device findings, rerun verification, and publish the first stable release.
